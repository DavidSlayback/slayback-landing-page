# slayback-landing-page

David Slayback's landing page. The hero is welding-spark physics in Rust → WebAssembly, flowing around the page's text; a Rumble Box–style game is next. Plan and decisions: [`docs/PLAN.md`](docs/PLAN.md).

## Layout

| Path | What |
|---|---|
| `crates/sim` | Pure Rust 2D particle physics (grains and sparks, uniform grid, text SDF obstacles, forcefield), the hero's wandering currents (exported for its GPU current layer), its centre of gravity, and the lettering's erosion (`erosion.rs`: the name is cut into irregular shards; strikes scorch it, a shard scorched through breaks off whole and the page drops it as a falling fragment; it re-welds at 40% gone). Native tests. |
| `crates/hero-wasm` | C-ABI WASM exports of `sim` for the browser (no wasm-bindgen; no imports). |
| `crates/game-core` | Engine-free game rules (combat, enemy brains, debris, the run, the input mapping in `controls` and the touch controls in `touch`, colours in `palette`, the floor movement and dash in `plane`, and what an agent sees and does in `agent`), in metres, m/s and seconds throughout. Native tests. |
| `crates/game3d` | The game at `/play` (spec #58, decisions Q46–Q64): Bevy 0.19 + avian3d 0.7, a shell over `game-core`. ## CI

Pull requests get one cheap `check` job: tests (including the headless game), clippy, and the hero build with its size budget. It runs only for non-draft PRs into `main`. PRs, stacked ones included, stay drafts while iterating; mark one ready only to merge it. The wasm game build, browser harness and deploys run on `main` (production, hero only) and on `rc/…` branches (a preview with the game). A newer run cancels an older one, so merging a stack builds once. See decisions Q41, Q42 and Q44.

Locally, pre-commit hooks are the gate (Q45). Install them once per clone: `uv tool install pre-commit && pre-commit install -t pre-commit -t pre-push`. Commits run hygiene checks, rustfmt and clippy; pushes add the tests, the wasm lint of the renderer modules and the hero size budget.

Deploying from this machine (when CI can't): `bash scripts/deploy.sh` ships production, hero only. `bash scripts/deploy.sh rc <n>` ships a preview of the full game at `https://rc-<n>.slayback.pages.dev`. There is one preview, with everything unmerged on one branch: `rc 5` (David, 2026-10-15). Each one runs the browser harness on exactly the build it ships and refuses to deploy on a failure. Production takes about 20 s; a preview takes as long as the game build. Both need wrangler logged in, or credentials in `.env.local`. While CI is unavailable, merge once the local hooks pass and deploy right after.

## Develop

```sh
cargo test --workspace --release        # physics tests
cargo run -p sim --release --example bench
bash scripts/build.sh                   # → dist/
python -m http.server -d dist 8080      # preview at http://localhost:8080 (add ?hud=1 for timings)
```

### Game dev loop

```sh
cd crates/game3d && trunk serve        # http://127.0.0.1:8091, rebuilds and reloads on save
```

Uses the fast `dev` profile: no LTO, no debug info, our crates at `-O1`, dependencies at `-O2`. Measured on this machine: the first build takes ~6 min. After that, an edit reaches a reloaded tab in **~14 s** (game crate) to **~16 s** (`game-core`), as measured on the 2.5D game. The size-optimised `game` profile (~10 min cold) is used only by `scripts/build.sh`, CI and deploys. `trunk` 0.21.14 comes from its prebuilt release; it fetches a matching `wasm-bindgen` if needed.

For feel-tuning, the game also runs natively in a desktop window:

```sh
bash scripts/native.sh                  # cargo run -p game3d; other args go to cargo: native.sh test -p game3d
```

On a Windows GNU-host toolchain the only install is `rustup component add llvm-tools`. The script copies the toolchain's own `rust-lld` (as `ld`) and `llvm-dlltool` into `target/native-tools/` and links with LLD. This is needed because GNU ld mislinks the `raw-dylib` import libraries that Bevy's Windows crates need, and the exe crashes at startup. No MSVC, nothing global, and wasm and CI builds are unchanged. On other hosts it is plain `cargo`. Measured: the first build takes ~7.5 min; rebuilds take ~17 s after a game-crate edit and ~6 s after a `game-core` edit.

Requires Rust stable with the `wasm32-unknown-unknown` target, Binaryen's `wasm-opt` (the build fails without it: the hero's 80 KB budget assumes it), and `wasm-bindgen` 0.2.129 (must match `Cargo.lock`) for the game. On a new machine, `bash scripts/doctor.sh` checks all of it, plus the pre-commit hooks and the harness's Chrome, and prints the install command for anything missing; deploys run it first. On a Windows GNU-host toolchain, install `wasm-bindgen` from its prebuilt release; building it with `cargo install` needs `dlltool`.

The first game build takes about 10 minutes (fat LTO for size); the web build is about 20 MB, or 6.2 MB gzipped (see Size under "The 3D game"). Throwaway design spikes live on the `spike/hero` branch.

`scripts/build.sh` honours `CARGO_TARGET_DIR`, so worktrees can share one target directory.

### Playing the game

**Controls.**

| Action | Keys |
|---|---|
| Run | WASD or the arrow keys, in eight directions |
| Dash | Space or Shift |
| Punch | J or left click |
| Kick | K or right click |
| Drop-kick | any attack during a dash |
| Grab | L or middle click: a live enemy or a debris part (frozen debris thaws) |
| Spin-throw | attack while holding; it hurts every enemy it passes through |
| Set down | L again |

Gamepads work too, with nothing to set up: left stick or d-pad to run, A or the right trigger to dash, X punch, Y kick, B grab, Start to pause or start, Select for sound on the pause screen (`crates/game3d/src/input.rs` maps every device to the same actions through the table in `game-core::controls`).

Touch screens play too (Q82, which replaced Q78's floating stick and gestures; `game-core::touch`, drawn by `touchpad.rs`), held sideways, with twin sticks always drawn at home in the bottom corners. A thumb landing on a stick's side centres that stick under it, so it starts still wherever the thumb lands; a thumb sliding past the stick's edge drags it along; let go, it goes home. The left stick moves; a thumb anywhere on the left half takes it. The right stick aims and attacks: pushed, the fighter turns that way and punches, again and again while it's held, so it can walk one way and punch another; carrying, it throws that way. Kick, Grab and Dash are three buttons arced above the right stick. A tap on the HUD (which shows a pause sign) pauses. On the pause screen a tap resumes, and a tap low on it toggles sound. A tap starts or restarts from the other screens, ignored for its first 0.6 s so a fight's last taps can't skip the game-over screen. On a touch screen the page fills the whole screen, still at most 1280×720 in layout. On Android the first touch also asks for full screen, held sideways, and a phone held upright is asked to turn.

There is no jump: you climb by stepping up debris (ledges up to 0.4 m).

**The box.**
- **Enemies** come in through four doors, two in the back wall and one in each side, which glow for 0.5 s first. They keep coming, often two doors at once, at Rumble Box's pace: box 1 holds 3 at first and climbs to 7 over 40 s, so standing still gets you killed (Q68). Who comes:
  - **Fodder** walk up and punch.
  - **Thugs** (from 14 s into box 1, like Rumble Box's heavies) are slow, wide and tough. Punches hurt them but don't interrupt their overhead smash; kicks, drop-kicks and throws do.
  - **Ninjas** (from box 3) are fast and fragile. They strike, retreat, and won't stand in front of you; they circle round to your flank.
  - **Bomb-heads** (from box 2, any kind): when defeated, the head drops as a lit bomb. It blinks for 1.5 s, then blows, hurting everyone within 3 m and knocking debris loose (never deleting it). You can grab and throw it.
- **Debris:** a defeated enemy bursts into its pieces (11 for fodder, 14 for a thug, 9 for a ninja), which freeze after 1.5 s at rest and become solid terrain. The player steps up ledges of up to 0.4 m, so piles are climbable. At most 300 pieces move at once and 1,500 stay frozen; the oldest go first (Q52).

**The run** (`game-core::run`) is endless. These numbers are first guesses for the playtest (Q29).
- **Escape:** heap debris against a wall and climb it: when the pile under you reaches the rim, with you within 0.8 m of the wall, the next box loads (a pile out in the middle is no way out, Q81).
- **Each new box:** a higher rim (1.5 m in box 1, then +0.48 m a box up to 3 m), a shorter timer, a bigger crowd (box 1 ramps 3 to 7 over 40 s, box 2 5 to 8, box 3 7 to 9, then 7 to 10), doors called more often (every 1 s in box 1, 0.1 s sooner a box down to 0.6 s; up to 2 doors at once, 3 from box 3), and the next of Rumble Box's looks (`palette::STAGES`, Q75).
- **Timer:** running out costs 25 health and restarts the clock.
- **Health:** escaping refills 30%; dying restarts at box 1.

**Demo mode.** `/play/?demo=1` plays a scripted fight, driving the game with the same actions a player's input produces: punch, kick, drop-kick and spin-throw. `&tour=1` plays the tour instead: a mini box (rim 0.7 m) where the player runs round, lands each move, walks to the right wall and heaps more kills against it, grabs a block and sets it on the heap, then climbs out over the wall (14 to 23 s of play; tested headless at 30 to 300 fps). `&rim=0.8` sets the first box's rim for any demo. Add `&slow=0.25` for slow motion (for recording a clip), `&debris=1000` to load the box with debris, or `&enemy=thug|ninja` and `&bombs=1` to change who steps up. Natively, run `DEMO=1 SLOW=0.25 bash scripts/native.sh`.

**The look** (Q50, Q66): flat-shaded cubes with thick black outlines and Rumble Box's tiled floor and walls, one small flat-shading material (`flat.rs`: a fixed key light plus ambient, no shadow map, no bloom, no tonemapping), so the fighters' colours stay saturated (G1, G4 and the feel pass below).
- **Resolution:** `site/play/` caps the canvas at a 16:9 stage of 1280×720 CSS px and scales it up with a CSS transform; the game ignores the display's pixel ratio. The backbuffer therefore never exceeds 1280×720.
- **Reduced motion and quality scaling:** see G9 below. The browser harness checks that the game picks reduced motion up.
- **Shapes, not just colours** (Q35): thugs are broad, ninjas slim, and bomb-heads have a bomb for a head (G5, G7).
- **Colours:** Rumble Box's own (Q75), not the hero's schemes. `?stage=N` starts the run N looks on, to review a box's look.

### Score and screens

A run starts from an overlay that states the goal (beaten enemies break into blocks; grab them, heap them and climb to the rim) and lists the controls. Esc pauses, and so does the page losing focus; the pause screen shows the goal and the controls again (Q80). Both screens play the tour clip beside their text (`site/play/tour.mp4`, the tour at 2.5x speed): the game sets `html[data-phase]`, and the play page shows the video only on those screens, in the slot `screens::CLIP` leaves free. Re-record it after a gameplay change: `SLOW=0.2 SECONDS=24 PAGE='/play/?demo=1&tour=1&slow=0.2' node record-clip.mjs <dir>` from `tests/e2e`, then `ffmpeg -i <dir>/clip.mp4 -vf setpts=PTS/2.5 -r 30 -c:v libx264 -crf 28 -pix_fmt yuv420p -movflags +faststart -an site/play/tour.mp4` (and the poster to `site/play/tour.jpg`). The first kill of a run brings up a tip that the blocks can be grabbed, until the player first grabs one (`hint.rs`, Q80). Under the HUD, a climb gauge shows how high the pile under the player stands against the rim, with a tick at the tallest heap in the box (`run::Climb`, Q80). The HUD shows health, box, timer and score.
- **Score** (`game-core::score`): each kill is worth 100 × a streak multiplier. Kills within 2.5 s of each other step it up (×1.5, ×2, up to ×4). Escaping adds 10 points per second left × the box number.
- **Game over:** shows the score, the box reached, and the best run. The best is stored as `v1;score;box;date` in localStorage (`slayback-best`), or natively in the temp directory.
- **Sound** (Q79): off by default; M on the pause screen toggles it, and the choice is kept (`slayback-sound`). Crunchy and real: blows thump, kills crack apart, debris knocks and clatters as it lands, doors knock twice, throws and bursts whoosh, bombs boom over rubble. The hits are recordings David picked by ear from CC0 packs on OpenGameArt (Independent.nu's punches, rubberduck's breaking and falling) and Kenney (`bash tools/sfx/import.sh <folder>`); the whoosh and boom are synthesised by `python tools/sfx/generate.py` (deterministic). All are 16-bit 44.1 kHz WAVs in `crates/game3d/assets/sfx/` (sources and credits in its README), embedded in the game. A browser keeps a page's audio suspended until the visitor interacts, so the play page resumes the game's audio on the first click, key or tap.

### The 3D game

`crates/game3d` is the game: a full-3D rebuild, Rumble Box style (spec #58, tickets #59–#70), that replaced the 2.5D game once it reached parity (G10, Q64). `docs/planning/parity-3d.md` maps each of the 2.5D game's 26 headless scenarios to its 3D counterpart. The 2.5D game lives on only in git history: its rc-1 archive was deleted on 2026-10-17 at David's request.

- **Build:** `bash scripts/build.sh` puts the game at `dist/play/` as `game.js` and `game_bg.wasm`, which `site/play/` hosts.
- **Preview:** `bash scripts/deploy.sh rc 5` builds it with the release switch on, runs the browser harness on that build, and ships `https://rc-5.slayback.pages.dev`, the one preview of everything unmerged. Production is unchanged: hero only, switch off.
- **G1:**
  - **The box:** a 15 × 10 m floor (3:2, Q56; about eight fighters across) with walls up to the rim (G3 sets it box by box). Every wall collides at full height; the front one is drawn as glass, a faint pane with black edges (Q57). Black tile lines run every metre across the floor and up the walls, and a thick black bar along the rim. Beyond each solid wall the ground outside the box stretches away at the rim's height (Q81), so the bar reads as the lip of the pit; it hides with its wall when the camera swings behind it. A wall (and its doors) the camera is behind turns to glass, so it never hides the fight. The camera always looks in over the front glass, so its top rail goes while the player is within 2 m of it.
  - **The camera** (Q65, after Rumble Box's video; `docs/research/rumble-box-reference.md`): yawed 30° off the box's axis so a back corner is in view, swinging ±35° away from whichever side wall the player nears, so that wall stays behind the player; 38° down from 12 m while roaming, dropping to 30° from 9.5 m when an enemy is within 4 m, leaning toward the fight; 40° field of view. Each box opens with a swoop up from the floor. It eases on real time, so it keeps moving through hit-stop. Movement is camera-relative (`input::ViewYaw`): up on the keys or stick is up the screen. The demo writes its moves in world terms straight into `input::Actions`, so the camera doesn't turn them.
  - **The player:** moves in eight directions at 6 m/s (WASD or arrows, or the left stick or d-pad, through the shared mapping in `game-core::controls`). It turns smoothly to face its last move and has a cyan ring on the floor (Q49, Q60). G3 makes its body a move-and-slide controller that climbs the pile.
  - **The look:** every mesh wears `flat::Flat` (Q74): its colour Lambert-shaded by a fixed key light plus ambient, fitted to how Bevy's `StandardMaterial` lit the box so the look didn't change, or unlit at full strength, plus a glow (a lit bomb's blink). The PBR shader took ~3 s to link on ANGLE/D3D11 at load; this one links in milliseconds, and the load has no GPU stall left. No lights in the scene, no tonemapping (Q66). Flat-shaded slabs and cubes, with a dark disc under the player standing in for a shadow (research §7).
- **G2, fighting:**
  - **Blows:** J punches and K kicks; either during a dash (Space or Shift, `game-core::plane::Dash`) is a drop-kick. Each hits a 100° cone in front of the player, reaching the 2.5D move's reach past the body (a punch about 1.4 m from the centre), level targets only. Aim assist snaps the swing toward the nearest enemy inside the cone, and bends a drop-kick's dash after it (`game-core::aim`). Timings, damage, hit-stop and the finisher freeze are the 2.5D rules (`game-core::combat`).
  - **Fodder:** eleven cubes and a ball head (`game-core::debris::solid::FODDER`), in Rumble Box's fodder colours: magenta, a peach head, brown legs (`paint::colour`, from `game-core::palette`). They enter through four doors, two in the back wall and one in each side (Q58), whose panels pulse for 0.5 s first. `enemy::Waves` keeps the box's crowd (`game-core::run::Run::crowd`, ramping from the spec's `crowd` to its `peak` over `RAMP`, 40 s, which a timeout doesn't reset) topped up: every `interval` it calls at up to `burst` free doors at once, counting enemies already on their way in. The numbers follow the counts in `docs/research/rumble-box-reference.md` ("Pace, counted"). They steer at the player while keeping apart and off the walls (`game-core::steer`, Q63), then telegraph (arm back, lit) and punch on the 2.5D brain's timings. Fighters pass through each other, so a crowd can't pin the player.
  - **Debris:** a defeat bursts the figure into its pieces with an outward fling and spin (damped, so heaps stay near where the figure fell and the ball head stops rolling). A piece freezes to static after 1.5 s at rest (or 6 s loose). At most 300 move at once (the oldest moving freeze early) and 1,500 stay frozen (the oldest go), per S2.
  - **Impact and HUD:** trauma shake (quadratic, real time, `impact::Shake`), a star burst at the point of contact, a squash on the victim, kill points floating up with the streak (`game-core::score`), and a health bar with the score. The feel rules are shared with the 2.5D game in `game-core::impact`.
- **G3, climbing and the run:**
  - **The controller** (`player.rs`): the player is a kinematic capsule moved once per physics step by avian's `MoveAndSlide`. It slides along walls and debris, falls under gravity and lands, walks up slopes up to 50° and steps up ledges up to 0.4 m with no jump (Q59; `game-core::climb`). That height is the fodder's torso block standing on end, so any piece lying on the floor is a step and a pile must be built up as a ramp. Input sets its floor velocity, and knockback sets all of it. It stands on a block's edge, and walks down piles without hopping.
  - **Escape** (Q51, Q81): when the pile under the player's footprint reaches the rim with the player within `game_core::run::AT_WALL` (0.8 m) of a wall, the box is escaped. `game-core::climb::pile_height` takes the debris pieces as data (cubes and balls, any rotation) and returns the highest surface under the footprint at or below the feet. Only debris counts, and an invisible fence on every wall keeps the player and flung pieces from going over the rim.
  - **The run** (`run.rs`, rules in `game-core::run` as in the 2.5D game): boxes in sequence, one life. Each box has a shorter timer and a busier crowd, and the console logs `box N started` with its rim, clock and crowd. Escaping refills 30% health, adds the time bonus, empties the box and rebuilds it at the next rim. Running out of time costs 25 health and restarts the clock (Q27). A death ends the run on the game-over screen (G8). The HUD shows the box and its clock.
  - **The rim** (`game-core::run::BoxSpec::rim`): 1.5 m in box 1, then +0.48 m a box (the 2.5D curve scaled), levelling off at 3 m. The 2.5D rims (4.4 m and up) are out of reach in 3D, where a pile grows with the cube root of its volume. Measured headless: 25 fodder killed in one spot heap to ~2 m, and the player climbs ~1.8 m of it. The same kills spread over 2 m reach ~1.2 m. 50 in one spot reach ~3 m.
  - **Demo stairs run:** `/play/?demo=1&stairs=1` (natively `DEMO=1 STAIRS=1`) disables enemies, builds a staircase of 0.3 m steps up to each rim, and walks the player right, out of box after box. The browser harness's scripted climb uses it. G9 adds the rest of demo mode (below).
  - **Not yet:** enemies are still dynamic capsules that stop at a pile's foot.
- **G6, grab and spin-throw** (`carry.rs`, the only writer of the player's `Carry` and the held and thrown things' `Carried` and `Thrown`; rules in `game-core::grab`):
  - **Grab** (L, middle click or B): the nearest `Grabbable` thing in the blows' 100° cone within about a metre of the player's edge, between its feet and head. That is a live enemy or a debris part, and frozen debris thaws (it starts again as a fresh loose piece). It is held out in front in both fists at chest height (Q77), out of the physics world: it collides with nothing, and a held enemy neither thinks, swings nor glows to wind up. A held enemy is lifted off its feet, faces the player, tips back and sways, its legs kicking and arms reaching up (`pose::Act::Dangle`); it lands upright. Grab again to set it down in front. A lit bomb is `Grabbable(Held::Bomb)` (G7).
  - **Spin-throw** (attack while holding): the player turns toward the biggest enemy group within 30° of its facing (Q62; `grab::throw_heading`: enemies within the throw's range, grouped by gaps of at most 1.5 m, the nearer group on a tie), plants its feet and whirls the thing once round in 0.22 s, swinging it out from the fists to arm's length and down to the player's middle. It flies flat (no gravity) at 12 m/s for 0.9 s, about 11 m. Held and thrown things stay inside the walls.
  - **In flight** it passes through fighters and hurts every enemy whose body it passes, once each, swept between frames: the 2.5D damage (a body 16, a part 9), knockback along the throw, hit-stun, flash, a star burst, hit-stop with the finisher's longer freeze on a kill, and the kill's points. A thrown enemy is hurt (10) by its first impact. Then it lands as what it was: a stunned enemy, or loose debris that freezes and counts toward the caps again.
- **G4, the hybrid look (Q50):**
  - **Outlines:** `outline::plugin`, a post-process pass on the camera's own depth texture (spike S1): black, ~6 px silhouettes and ~4 px creases at 720p (Q66). WebGL2 forces MSAA off and a NEAREST depth sampler; no FXAA.
  - **Colours:** Rumble Box's (Q75); the rules live in `game-core::palette`. Fighters wear fixed colours by part (`fighter`: body, head, fist, trim); each box is a `Stage` (sky, two tile colours, line colour), cycling green tiles, orange checker, grey checker, dark blue; debris is a pale wash of its part's colour toward the floor (`debris`); the ring is cyan, the health bar green, and door warnings, impact bursts and score popups red (`SIGNAL`). The `flat` material checkers the floor and walls in the shader, from the floor's corner a tile a metre. `look::Palette` holds the box's stage and changes on `BoxStarted`. `paint.rs` holds every colour rule (`paint::colour` by `paint::Role`) and one shared material per role, repainted in one place (the clear colour too); door warnings and lit bombs' blinks animate their own colours but take them from `paint::colour`. A pre-commit check keeps the rules' names out of the rest of `game3d`.
  - **Figures and motion** (`figure.rs`, `pose.rs`; Q61, Q65-Q69): one path dresses, colours and animates every fighter. The player is loose parts (`figure::PLAYER`: ball head and fists, a four-cube torso, two cubes to each leg) in contrasting colours; enemies are their `game-core` pieces; parts are drawn smaller (0.62 enemies, 0.76 player) and spread 25% sideways so gaps show (Q71, Q73). `pose` moves them all: a punch twists away, then lunges and snaps the arm out in an arc to full reach in ~0.1 s with the torso turning ~40° through it; a kick turns the hip through, holds and pulls back (the player alternates arms; its punch, kick and drop-kick reach 70% further than the fodder's `Jab`, Q70/Q73); kicks, drop-kicks, a held thing in the fists, a held enemy dangling, the whirl and the throw's follow-through; a snappy walk with a bob. Parts ease toward their pose (33 ms) on the game clock, so hit-stop freezes them. WebGL builds a render pipeline the first time a material is drawn, which froze the first hit for 3.6 s; `camera::Warm` draws the burst, flash and popup text once while the page loads (Q72), and the burst's star carries UVs so it shares the cubes' shader instead of needing its own 3.4 s compile (Q73). The one remaining long compile (~3 s on ANGLE/D3D11) runs behind the static start screen. What a figure does each frame is one pure function, `pose::look(&mut Motion, &FigureState, dt) -> Look`, tested headless: its turn (a whirl's from the throw's heading), lift, lean and squash, each limb's pose with an enemy's wind-up, and its tint (the hit flash over everything, softer under reduced motion, then an enemy's wind-up glow, then its own paint). `figure::animate` only gathers the state and writes the look; it is the only writer of a figure's rig.
- **G8, screens, score and sound** (as in the 2.5D game, Q34/Q35):
  - **Phases** (`flow.rs`): a fresh page opens on the start overlay with the controls (`screens.rs`); a click, Enter, Space or Start begins. Esc pauses, and so does the page losing focus; the pause screen has the sound toggle. Anything but playing pauses the game clock, so physics, the box clock, swings and streaks all stop. A death (a blow or the clock) shows the game-over screen with the score, the box reached and the best, flagged when the run set it; a click or Enter starts a fresh run at box 1. The console logs `phase start`, `phase playing` and so on for the browser harness.
  - **Best score** (`score.rs`): the 2.5D game's record (`game-core::score::Best`, `v1;score;box;date`) under the same key, `slayback-best`, so a best set in the 2.5D game still counts. `store.rs` keeps it in localStorage, or natively in a file in the temp directory; headless scenarios give each test its own directory.
  - **Sound** (`sound.rs`; replaced by Q79's wooden set, see above): a thump per blow (three takes each of a light and a heavy one, jittered in pitch), a crack (two takes) and a whoosh per kill, a whoosh per throw, debris knocks from `debris::Clack` (a loose piece whose velocity jumps beyond gravity's pull; the two hardest a frame, at most one batch every 30 ms, louder the harder, higher the smaller), a double knock as a door starts warning, and a boom over rubble per blast. Off by default; M on the pause screen toggles it, kept under `slayback-sound` as in the 2.5D game.
  - **Demo:** `?demo=1` goes straight into play with no overlay and doesn't pause on blur, as in the 2.5D demo.
- **G7, bomb-heads** (`bomb.rs`, rules in `game-core::bomb`, the blast by 3D distance):
  - **Bomb-heads:** each door entry is one with the box spec's chance (none in box 1, 15% in box 2, rising to 30%), as in the 2.5D game. A bomb-head wears a dark faceted bomb with a glowing fuse stub in place of its ball head (a shape cue, Q35). On defeat the head drops free as a lit bomb and the other ten pieces burst into debris as usual.
  - **Lit bombs:** the 2.5D fuse (1.5 s) and blink (3 Hz rising to 12 Hz, the whole shell lighting in the warning accent). The blast reaches 3 m in 3D (not the 2.5D 4.4 m converted, which would cover two-fifths of the box), with the 2.5D damage (32 at the centre to 8 at the edge) and launch falloff fed the full 3D distance, pushed away across the floor and up a little (scaled as blows are). It hurts and launches everyone in range, the player included, with a 0.12 s hit-stop, the strongest shake (`BLAST_TRAUMA`) and the biggest star burst. Other lit bombs in range go off 0.15 s later (`CHAIN`), so chains ripple; a bomb-head the blast kills drops a fresh one. Debris in range thaws and is flung, never deleted; past the moving cap the farthest freeze again first. Each blast sends `bomb::Exploded` (for the sound).
  - **Grab and throw:** a lit bomb grabs, carries and spin-throws like anything else, its fuse burning on in hand; a live (stunned or not) bomb-head grabs as an enemy, and drops its bomb wherever it is defeated. A thrown bomb clips each enemy it passes (4 damage), but stops dead at the first one it hits and drops there, as the 2.5D bomb bounced off the first body (`grab::stops`), so it lies in the group until it blows on its fuse.
  - **Demo:** `/play/?demo=1&bombs=1` (natively `DEMO=1 BOMBS=1`) makes every enemy that comes through a door a bomb-head; with G9's scripted fight (no doors), the enemies that step up are bomb-heads.
- **G5, thugs and ninjas** (`enemy.rs` and `figure.rs`; brains, timings and armour from `game-core::enemy` as in the 2.5D game, figures in `game-core::debris::solid`, steering in `game-core::steer`):

Slow (0.3 of the player's speed) with 60 health. They plough straight at the player, ignoring the crowd, while the others steer round them. Armour: a punch hurts but neither staggers nor moves a thug, so its 0.6 s wind-up (the striking arm raised overhead, lit) carries on into the smash; a kick, drop-kick or throw staggers it and resets the wind-up.
  - **Ninjas:** 9 pieces (a ball head, slim torso and sash, one long cube to each arm, two to each leg), 1.5 m tall on a 0.3 m capsule. Fast (1.25 times the player's speed) and fragile (18 health). - **G9, gamepad, comfort and demo mode** (as in the 2.5D game, Q35):

Fodder are placed on top of the pile, not inside it. Unless `hp` or `timer` is set, the player's health and the box clock are topped up when low, so the fight runs as long as the page is open. ## Game release switch

Visitors can't find the game until it ships. `GAME_RELEASE=1 bash scripts/build.sh` turns on its entry points:

- a **Play** item in the nav and a small **Play the game** call to action under the tagline (a `data-collide` hero element, so the sparks flow around it), both linking to `/play/`;
- an easter egg: the Konami code (↑ ↑ ↓ ↓ ← → ← → B A) on the homepage opens `/play/`;
- the clip page `/play/watch/`, a looping gameplay clip with a "Play on a computer" note. Touch devices were sent there until Q78 gave the game touch controls; nothing links to it now.

The switch is off by default, and deploys never set it. Off, the homepage is byte-for-byte the pre-switch page. In `site/`, switch-only content sits between `<!-- GAME_RELEASE -->` and `<!-- /GAME_RELEASE -->` markers (`/* … */` in CSS and JS), on their own lines or inline. The build deletes the marked content when the switch is off and only the markers when it is on. The switch needs the game, so the build refuses `GAME_RELEASE=1` with `SKIP_GAME=1`.

The clip (`site/play/watch/clip.mp4` plus `poster.jpg`) is six seconds of the real game: the scripted demo fight, recorded by `tests/e2e/record-clip.mjs` in its slow-motion mode. The page runs at `slow=0.2`; the recorder screenshots as fast as it can and times each frame back to game speed, then encodes 640×360 H.264, muted, at about 40 KB (re-recorded from the 3D game in G10). The recorder's frame-exact mode (`?capture=1`) still serves the hero.

```sh
bash scripts/build.sh && cd tests/e2e && npm ci          # a build with the game
SLOW=0.2 PAGE='/play/?demo=1&slow=0.2' node record-clip.mjs   # → site/play/watch/clip.mp4 + poster.jpg (needs ffmpeg and a game build)
```

## Browser tests

Playwright smoke checks in `tests/e2e/` run against the built `dist/`: the homepage renders with no console errors, the no-WebGL fallback keeps readable text, reduced motion shows a still frame, `/play` loads cleanly (skipped when the build has no game), and the release switch behaves (see above).

```sh
SKIP_GAME=1 bash scripts/build.sh       # or a full build to cover /play
cd tests/e2e && npm ci && npx playwright test
```

Locally it uses the installed Chrome (`PW_CHANNEL=` to use a Playwright-managed browser) with SwiftShader WebGL, so no GPU is needed; `DIST=<dir>` tests another build. Set `GAME_RELEASE=1` when testing a switch-on build: the switch-off checks (no Play link, no clip page, an inert easter egg) run otherwise. The game checks (load, start overlay and pause, scripted climb, reduced motion, demo fight) run when the build has the game and skip otherwise; `REQUIRE_GAME=1` makes a missing game a failure. CI's `browser` job runs on `main` and `rc/` branches (not on PRs): it tests the full switch-on build and the hero-only `dist` that main deploys.

Review tools in `tests/e2e/tools/` run a `dist/` build in Chrome on the real GPU (`--swiftshader` to opt out): `shot.mjs` screenshots a still page (the homepage, a write-up) at several viewport sizes, `capture.mjs` tiles frames into a sheet for frame-by-frame review, `frametime.mjs` reports slow frames, median and p99, and `trace-shaders.mjs` counts shader links and GPU stalls from page load. `shaders.spec.js` in the harness fails if any shader links once the warm-up is drawn.
